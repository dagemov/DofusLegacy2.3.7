Admin Tools Migration Master Plan

Date: 2026-05-31 | Repo baseline: DofusLegacy2.3.7 | Planning branch: feature/admin-tools-migration-master-plan

This plan formalizes the current repo as the only destination for the next admin stack. Legacy Blazor remains a logic reference. The previous Angular/Admin API repo remains the primary contracts-and-patterns reference. No mass copy of code or assets is part of this phase.

Keep main and Yaco No direct MySQL from browser No Blazor as final UI stack No secret commits

Git Baseline

Remote validation on 2026-05-31 showed that origin/main already contains origin/Yaco. The promotion happened indirectly through merged PR #8 (Yaco -> devp) and merged PR #9 (devp -> main).

Because there is no remaining diff for a direct Yaco -> main PR, the effective baseline for planning is the updated main branch, while Yaco remains preserved as a stable branch.

Current Reality

  • Sunshine net11.0/ holds the emulator runtime.
  • OneLauncher/OneLauncher.Api already serves launcher-facing auth and HTTP endpoints.
  • RollblackLegacy.Auth and RollblackLegacy.Website* already provide account flow building blocks.
  • No RollblackLegacy.Admin.* projects exist yet.
  • No Angular admin workspace exists inside the current repo yet.

Recommended First Module

After the baseline architecture and website/auth alignment, the first functional migration should be Items Builder.

  • It has the richest validated legacy logic.
  • It exercises PNG preview and client metadata without immediate gameplay risk.
  • It unlocks follow-up work for sets, vendors, and visual data hygiene.
  • It is materially safer than starting with spells or maps.

Execution Phases

Phase 1

Goal: Create RollblackLegacy.Admin.* projects and solution shape.

Close when: API/Application/Domain/Infrastructure/Contracts/Angular are defined in-repo.

Phase 2

Goal: Align website, launcher API, and future admin auth on the validated DB connection.

Close when: operator identity flow and local secret handling are explicit.

Phase 3

Goal: Port item create/edit, preview, PNG upload, and validation to Angular + API.

Close when: items no longer require raw SQL for normal admin work.

Phase 4

Goal: Port spells with levels, effects, class links, and glyph/trap rules.

Close when: save and publish flow has backups and in-game QA.

Phase 5

Goal: Reuse the prior Angular monster/family slices and adapt them to sunshine.

Close when: monster CRUD and core validations run through the new stack.

Phase 6

Goal: Reintroduce map and group tooling with read-first safety.

Close when: risky writes are explicit, guarded, and reversible.

Phase 7

Goal: Use launcher aesthetics as admin design guidance only.

Close when: design tokens are defined without copying launcher code or binaries.

Phase 8

Goal: Standardize DB, SSH, backup, and deploy workflow for the team.

Close when: every risky phase has backup and rollback rules.
